## Verified correct (running list)

- CORRECT: directives are signature-checked on both clients when code signing is configured (Android FileDownloader.kt:641-681 parseDirective -> validateSignature, throws "Code signing verification failed for directive"; iOS FileDownloader.swift:968-1042). So an attacker on the path cannot forge a far-future rollBackToEmbedded.
- CORRECT: chain mode terminates at the embedded root: Android builds the chain as served certs + embedded cert (CodeSigningConfiguration.kt:64-67), requires issuer/subject chaining and signature (CertificateChain.kt:83-96), root must be CA (basicConstraints>-1 and keyUsage keyCertSign, :79-81,:99-103), leaf must have digitalSignature + EKU codeSigning (:55-59). The plan's root (CA:true, pathlen:0, keyCertSign) and leaf (digitalSignature, EKU codeSigning) match these rules.
- CORRECT: an empty served chain in chain mode makes the embedded root the "leaf"; the plan's root has no digitalSignature/codeSigning EKU, so the root itself cannot sign manifests directly (CertificateChain.kt:39-41). Fine, but it means every manifest response MUST carry the certificate_chain part (the plan's table does send it).
- CORRECT: every certificate's validity is checked against the device clock (Android CertificateChain.kt:51 checkValidity; iOS CertificateChain.swift:76). The plan's "notBefore 24 h in the past" helps slow clocks; a phone whose clock is past the leaf notAfter simply rejects updates (no brick).
- CORRECT: with `metadata: {}` the unsigned `expo-manifest-filters` response header is inert: a filter only fails when the metadata HAS the key (Android SelectionPolicies.kt:36; iOS SelectionPolicies.swift:22-26).
- CORRECT: a rollBackToEmbedded directive applies only when directive.commitTime is after the launched update's commitTime, unless filters fail (Android LoaderSelectionPolicyFilterAware.kt:60-83).
- CORRECT: a 204 must carry expo-protocol-version > 0 (Android FileDownloader.kt:504-512); no signature is needed for a 204, so the plan's 204 paths are accepted by a code-signing client.
- CORRECT: the repo is PUBLIC and the default branch is main (`gh repo view`: visibility PUBLIC, defaultBranchRef main).
- CORRECT: repo variables today are DEPLOY_ENABLED=true and HEALTH_PORTS="8765 9090 9091"; DEPLOY_KNOWN_HOSTS exists as a repo secret (`gh variable list`, `gh secret list`, 2026-10-22).
- CORRECT: deploy.yml:127 uses `secrets.DEPLOY_KNOWN_HOSTS || '<pinned key>'`, so deleting the secret makes the expression fall back to the pinned ed25519 line (an unset secret evaluates to an empty string, which is falsy).
- CORRECT: the production environment has no protection rules and no branch policy (`gh api repos/{owner}/{repo}/environments`: protection_rules [], deployment_branch_policy null), so the plan is right not to put any key in Actions.
- CORRECT: the pinned host key in deploy.yml:127 equals the live key: `ssh-keyscan -p 2222 -t ed25519 35.226.215.209` on 2026-10-22 returned `[35.226.215.209]:2222 ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIJJ9b5k82WEzUca3oWtKKKdYIot4WVq6D2xStYxUJJyZ` (banner OpenSSH_10.0p2 Debian-7+deb13u2). ### F1 [BLOCKER] The Android release key is stored and used weaker than the OTA leaf, inside the npm/Gradle process tree
Quote: "Add the four `AM_RELEASE_*` lines to `~/.gradle/gradle.properties` and `chmod 600` it." (Phase 3.2) and "A config plugin, `mobile/plugins/withReleaseSigning.js`, adds `signingConfigs.release` from `AM_RELEASE_*` Gradle properties" (D10); also "You type the keystore and leaf passphrases." (6.1)
Problem: the store password sits in plaintext in ~/.gradle/gradle.properties next to the .p12 on the Mac's disk. `chmod 600` does not stop same-user processes, which is exactly the reason the plan gives for rejecting a 0600 OTA key ("every `npm ci` install script runs as the same user", D4 Rejected). Worse, signing happens INSIDE Gradle, whose build evaluates the build.gradle of every autolinked npm package (react-native-webrtc, incall-manager, expo-*), and those scripts can read any project property (`findProperty("AM_RELEASE_STORE_PASSWORD")`) and the keystore file; Gradle also spawns Node for autolinking during the build. So "after every Node process has exited" can never hold for the Android key. A malicious npm package gets a key that Android accepts as an in-place update of com.alexanderjia.messages (inherits the secure-store token and Keystore-sealed ring token) and that passes app-updater's "signer equals the installed app's signer" check. The key is permanent: revoking it needs another uninstall of every phone. It also lands in Time Machine/iCloud backups in usable form. 6.1 ("You type the keystore ... passphrases") contradicts 3.2 (password stored in a file).
Evidence: plan Phase 3.2, D4 Rejected list, D10, 6.1; Gradle evaluates autolinked subprojects in the same build (mobile/android/settings.gradle autolinking).
Correction: "Gradle builds an UNSIGNED release APK (no signingConfigs.release; withReleaseSigning.js only removes the debug signing from the release buildType and fails the build if any signingConfig is attached to release). After Gradle and every Node process have exited, `otapublish native` runs `zipalign -p 4` and `apksigner sign --ks ~/.alexmessages/keys/android-release.p12 --ks-pass stdin` itself, with the password typed at that prompt, then `apksigner verify --print-certs` against mobile/release/android-signer.sha256. No AM_RELEASE_* password is ever written to ~/.gradle/gradle.properties. The .p12 is kept age-encrypted on disk (~/.alexmessages/keys/android-release.p12.age) and decrypted to memory or a tmpfs-like 0600 temp file only for the apksigner call." 

F1 evidence addendum: mobile/android/settings.gradle:1-31 runs `node --print require.resolve(...)` through providers.exec during Gradle configuration and autolinks every native npm package as a subproject (`autolinkLibrariesFromCommand(expoAutolinking.rnConfigCommand)`); mobile/android/app/build.gradle:100-115 is where the release signingConfig would be read, in that same Gradle build.

### F2 [MAJOR] "All Node processes have exited" is not enforceable, and otapublish is compiled from the dirty main checkout
Quote: "11. All Node processes have exited. Ask for the leaf passphrase on the terminal" (D6) and "go run ./cmd/otapublish ota ..." (D6, §6); "Signing happens on the Mac only, inside `otapublish`, after every Node process has exited." (D4)
Problem: (a) otapublish can only wait for its own children. Any code that ran in steps 3, 4, 8 and 9 (npm ci, tsc, vitest, Metro/Babel plugins, app.config.js) can start a detached process (`spawn(..., {detached:true}).unref()`), which outlives npm and is still running at the passphrase prompt. (b) `go run ./cmd/otapublish` compiles cmd/otapublish and internal/ota from the developer's main working tree, not from the pushed commit that step 1 checks out. A same-user npm package that ran during everyday `npm install` in mobile/ can edit those .go files; an honest uncommitted edit to internal/ota also gets compiled. Either way the code that decrypts the leaf key is not the reviewed code.
Evidence: plan D6 steps 1-11; mobile/package-lock.json today has 0 packages with install scripts and shared/package-lock.json has 2 (esbuild, fsevents) (python scan of `hasInstallScript`), but Metro/Babel/tsc/vitest execute package code regardless of install scripts.
Correction: "Step 0: `otapublish` refuses to run unless it was built from the clean worktree of the pushed commit (`go build -o <tmp>/otapublish ./cmd/otapublish` inside that worktree BEFORE any npm step; the binary embeds its commit through -ldflags and checks it equals the worktree HEAD). Steps 3-10 run with `npm ci --ignore-scripts`. Before step 11, otapublish lists every process of the current user whose executable is node, npm, npx, esbuild, watchman or java (`ps -U $(id -u) -o pid,comm`) and refuses to prompt for the passphrase while any exists. Better: run steps 3-10 as a separate macOS user (`sudo -u am-build`) that has no read access to ~/.alexmessages."

### F3 [MAJOR] iOS native updates (AltStore source, update banner, blocking screen) are unauthenticated; the plan claims every update is signed
Quote: "2. Every update is signed with a key that never sits on the Pi, the GCP relay, Cloudflare or GitHub. A phone rejects code that this key did not sign." (§0) and "The IPA stays unsigned; each user's sideload tool signs it. ... `/app/altstore.json` lists each IPA" (D10)
Problem: the IPA carries no developer signature, and SideStore/AltStore re-sign whatever IPA the source points to with the user's own Apple ID, so an iOS "update" from a tampered source is installed as the same app (same team, same bundle id) and inherits its Keychain token and data container. Whoever controls the Pi (root, Coolify), the relay (can get a TLS cert via HTTP-01) or Cloudflare can rewrite /app/altstore.json (its sha256 field is in the same file) and also /api/app/latest and the WS `client_policy`, which drive the in-app banner and the full-screen "no longer supported" screen that tells users to update. That is attacker native code on iPhones after one user tap, and the plan's app actively prompts for that tap. The source design said this plainly (designs/safety-first.md:414 "a compromised Pi could serve a malicious IPA to anyone who taps Update in SideStore"); the final plan dropped the sentence. Android is not affected the same way because app-updater checks the signer and Android enforces it.
Evidence: plan §0 item 2, D10 iOS, D10 Minimum-client gate (policy.json and client_policy are unsigned server data); designs/safety-first.md:49 and :414.
Correction: add to §0 "Not covered by the signature: iOS native updates. IPAs are unsigned, so a compromised Pi, relay or Cloudflare can offer a malicious IPA through the AltStore source." Then: (1) put the native-release record {platform, version, build, sha256} inside the signed OTA manifest (`extra.am.native`), and have the app show the iOS update banner and the `update_required` screen only when the signed record agrees with /api/app/latest; (2) show the expected IPA SHA-256 prefix in the banner; (3) `otapublish audit` (run daily from the Mac) compares altstore.json, policy.json and every IPA/APK hash on the Pi with the Mac archive and alerts on any difference.

### F4 [MAJOR] The census is unauthenticated, so both safety gates built on it can be forged
Quote: "`otapublish promote <label>` ... refuses unless the census shows at least one beta install per platform that has launched the update and reported no failure." (D5) and "Automatic halt (Phase 9, server only): the production pointer switches to `halted` (204 to everyone) when an install that is linked to an approved user, and was first seen before the activation, reports the active update as failed, or when `ota.crash` for it arrives from two installs within 60 minutes." (D8)
Problem: every census field comes from an anonymous GET: EAS-Client-ID, Expo-Current-Update-ID, Expo-Recent-Failed-Update-IDs, and `am_uid`, which the plan itself calls "a hint only, never used for access". (a) Promote gate: anyone can send one request per platform with `Expo-Current-Update-ID: <beta id>` and `am_channel="beta"`; the gate passes with no real phone. Also an honest stale row passes it. (b) Auto-halt: an attacker creates fake installs any time before an activation (rows are "first seen" then), claims `am_uid=<any small integer>` (user ids are sequential), reads the active update id from the public manifest, and reports it in Expo-Recent-Failed-Update-IDs. One request halts production for everyone, every time, including halting a security fix; `ota.crash` arrives through /api/debug/report, where identity is optional (server-deploy.md:71). Each trigger also sends a Web Push to admins.
Evidence: plan D5, D8 items 1 and "Automatic halt"; internal/debuglog/debuglog.go (anonymous reports accepted).
Correction: "The promote gate counts only installs whose current update id was also reported by an authenticated session: the `X-AM-Client` header on bearer-authenticated REST calls (stored in `sessions.client`) must show `update=<beta id>` for an approved admin's session. Automatic halt counts only failures reported over an authenticated channel (an `ota.crash`/`ota.boot` event sent by a signed-in approved user through REST, deduplicated per user, at least 2 distinct users), never Expo-Recent-Failed-Update-IDs or am_uid from the manifest request. Auto-halt acts on beta only; production halts stay manual."

### F5 [MAJOR] "Rate-limited per IP" is not possible with the current stack, so the anonymous census can fill the Pi's disk
Quote: "Header formats and sizes are validated, writes are rate-limited per IP, IPs are not stored, rows unseen for 90 days are pruned" (D8)
Problem: webapp uses `gin.New()` with no `SetTrustedProxies` (internal/webapp/webapp.go:36), and gin v1.12.0 trusts every proxy by default (gin.go:38-47 defaultTrustedCIDRs 0.0.0.0/0 and ::/0) and returns the LEFTMOST X-Forwarded-For entry (gin.go:482-500), which the client writes. The existing debuglog limiter uses exactly this (debuglog.go:251-259). If nginx overwrites XFF instead, the address is a Cloudflare edge (PROXY protocol from the relay carries the TCP peer), so every phone in a region shares one bucket. Either way an attacker gets unlimited inserts with random EAS-Client-IDs; each row holds up to 1024 chars of Expo-Fatal-Error plus ids, the prune runs only after 90 days, and the rows go into alexmessage.db on the Pi's SD card, the same file chat writes to. A full disk stops message writes. The origin also answers directly, bypassing Cloudflare (server-deploy.md:17), so CF-Connecting-IP is spoofable too.
Evidence: internal/webapp/webapp.go:36; gin@v1.12.0/gin.go:38-47, 214-226, 482-500; internal/debuglog/debuglog.go:251-259; reports/server-deploy.md:17.
Correction: "Census writes have a hard global cap: at most 5,000 rows in `ota_installs`; when full, existing rows are updated and new ones are dropped with one `ota.census_full` debug event per hour. The census lives in its own file `data/ota/census.db`, not in alexmessage.db. A row is created only when Expo-Embedded-Update-ID equals the embedded update id of a registered binary (read from the artifact at `otapublish native`). The per-IP limiter uses `CF-Connecting-IP` only after `r.SetTrustedProxies(nil)` and nginx `set_real_ip_from` for Cloudflare's published ranges, and the origin firewall/nginx refuses non-Cloudflare peers on 443."

### F6 [MAJOR] Pre-signed rollBackToEmbedded directives on the Pi give anyone who controls the Pi, relay or Cloudflare a fleet-wide downgrade that outlives the attack
Quote: "rollback.json, rollback.sig  rollBackToEmbedded, commitTime = createdAt + 1 s" (D2 storage) and "The Pi never signs anything and holds no private key. It serves bytes that the Mac signed." (§2)
Problem: a directive applies to every phone whose launched commitTime is earlier than the directive's (LoaderSelectionPolicyFilterAware.kt:60-83), and it stays valid until its leaf expires (up to 400 days). Serving the newest update's stored directive sends every phone back to its embedded JS; the client then rewrites the embedded update's commitTime to the directive's (reports/expo-updates-sdk57.md:447), so after the attacker is gone the phones still refuse the legitimate current update until a Mac republish. The plan's own rule ("`rollback-embedded` is allowed only while the server still works with the embedded JS", D9) shows this can break the app fleet-wide, and it re-exposes any client bug fixed by OTA after the binary was built. The plan does not list this capability in its threat statements.
Evidence: plan D2, D9 rule; expo-updates Android LoaderSelectionPolicyFilterAware.kt:60-83; reports/expo-updates-sdk57.md:443-449.
Correction: either (a) keep rollback.json/.sig only in the Mac archive and in the password manager (not in data/ota on the Pi), and make the emergency step "upload the stored directive with `scp`, then `otactl rollback-embedded --directive <file>`"; or (b) keep them on the Pi and add to §0/D4: "Anyone who controls the Pi, the relay or Cloudflare can roll every phone back to its built-in JS until you republish from the Mac; `otapublish audit` alerts when a pointer is in `rollback` state that the Mac did not set." State which one is chosen.

### F7 [MAJOR] The store does not record which leaf signed each signature, and rotation does not cover the stored rollback directives
Quote: "certs/root-2026.pem, leaf-<yyyymm>.pem  public certificates only" (D2), "a `certificate_chain` part (the leaf certificate)" (D2 table), "`otapublish resign-active` (re-signs every manifest and directive that a pointer references; the bodies stay byte-identical)" (D4)
Problem: during and after a rotation there are two leaves in certs/, and the endpoint must send the leaf that made THAT signature. The layout has no per-signature leaf id, so the server either guesses or sends the newest leaf; a manifest signed by the old leaf served with the new leaf fails verification on every phone (CodeSigningConfiguration.kt:63-101 verifies with the chain's leaf key). Separately, a pointer in `update` state references the update, not its rollback.json; if resign-active skips it, then after the old leaf expires the emergency `otactl rollback-embedded` serves a directive signed by an expired leaf, every phone rejects it (CertificateChain.kt:51 checkValidity), and the emergency rollback silently does nothing.
Evidence: plan D2 storage tree and table, D4 rotation bullet; expo-updates Android CodeSigningConfiguration.kt:63-101, CertificateChain.kt:46-53.
Correction: "Each signature file has a sibling naming its signer: manifest.sig + manifest.leaf, rollback.sig + rollback.leaf (the leaf certificate's SHA-256). The endpoint sends exactly that leaf. `resign-active` re-signs, for every update referenced by any pointer (production and beta) and for the last 3 updates per platform/runtime, both manifest.json and rollback.json. `otactl activate` and `otactl rollback-embedded` refuse a signature whose leaf expires within 30 days, and `otactl doctor` checks the leaf of every pointer-referenced manifest AND its rollback directive."

### F11 [MAJOR] The §9 fallback ("put them in `metadata`") turns the unsigned `expo-manifest-filters` header into a downgrade/replay switch
Quote: "`Updates.manifest.extra.am` (label, notes, critical) is readable in JS | scenario a; fallback: put them in `metadata` as strings" (§9)
Problem: `expo-manifest-filters` is a response header outside the signature. With `metadata: {}` it does nothing (a filter fails only when the metadata has the key: SelectionPolicies.kt:36, SelectionPolicies.swift:22-26). Once metadata has keys such as `label` or `critical`, anyone on the delivery path can send `expo-manifest-filters: label="x"`; the launched update then "doesn't pass the manifest filters", and the client loads a new update "no matter the commitTime" (LoaderSelectionPolicyFilterAware.kt:31-35) and rolls back to embedded unconditionally (:76-79). That re-enables replay of any older signed update for the runtime, including ones in revoked.txt, which is enforced only by the Pi.
Evidence: expo-updates Android SelectionPolicies.kt:15-46, LoaderSelectionPolicyFilterAware.kt:16-83, LauncherSelectionPolicyFilterAware.kt:18-25; iOS SelectionPolicies.swift:8-35.
Correction: replace the fallback with: "fallback: read label/notes/critical from `Updates.manifest` (the full signed manifest) or from a small signed asset; `metadata` stays `{}` forever, and `otactl ingest` and the Go tests reject any manifest whose `metadata` is not `{}`."

### F12 [MINOR] app-updater: verify-then-stream leaves a gap, and the package check is not enforced by the OS
Quote: "It downloads the APK with Range resume, checks the SHA-256, then checks with `getPackageArchiveInfo(GET_SIGNING_CERTIFICATES)` that the package is `com.alexanderjia.messages` ... It installs through a `PackageInstaller` session ... Even malicious JS can only install a newer build of this app signed with your key." (D10)
Problem: the file is checked on disk, then reopened and copied into the session. Any same-UID code can rewrite it in between; JS can, through expo-file-system, whose permission service grants WRITE to filesDir and cacheDir and to any other path the process can write (expo-modules-core FilePermissionService.kt:18-40), so moving the file to no_backup does not hide it. For an update of the same package the OS still enforces the signer and blocks downgrades, but a swapped APK with a DIFFERENT package becomes a new-app install behind one system prompt. So "only a newer build of this app" is not guaranteed by the design as written. Also the sha256 comes from JS (`downloadAndInstall(url, sha256, minBuild)`), i.e. from the unsigned /api/app/latest, so it protects against corruption, not against an attacker.
Evidence: plan D10; mobile/node_modules/expo-modules-core/android/src/main/java/expo/modules/kotlin/services/FilePermissionService.kt:18-40.
Correction: "app-updater opens the downloaded file once and streams it into the session while hashing; it abandons the session on a hash mismatch. It sets `SessionParams.setAppPackageName("com.alexanderjia.messages")` so the OS fails the install for any other package, and keeps the getPackageArchiveInfo signer/versionCode check as a pre-check only. Malicious JS can then at most install a newer build of this app signed with your key."

### F13 [MAJOR] Android developer verification (2027) is not in the plan
Quote: "Android: from build 3 on, native updates install from inside the app (one tap, or no tap on Android 12+ in a later build)." (§0 item 4) and D10 Android.
Problem: Google requires apps installed on certified Android devices to come from a registered developer: from 2026-09-30 in Brazil, Indonesia, Singapore and Thailand, and globally from 2027 (androidauthority.com/android-sideloading-changes-timeline-3679204, June 2026). Installs through adb and an "advanced flow" stay possible, and free limited-distribution ("hobbyist") accounts allow up to 20 devices. Phones with Google Play services (your own Android phone, any non-Chinese user) would then refuse both the /app download and the in-app PackageInstaller update of an unregistered package. Phones without Google Play (the China phones) are not certified devices and are not affected (inference). ## Findings

### F1 (major) D9 automatic recovery overstated
Quote: "an update that crashes before its first screen is marked failed on that phone and never launched there again; the phone falls back to the last update that launched successfully, or to the embedded bundle."
Evidence: iOS PKG/ios/EXUpdates/ErrorRecovery.swift:159-164 and Android PKG/android/.../errorrecovery/ErrorRecoveryHandler.kt:116-122 mark the update failed ONLY when `successfulLaunchCount == 0` and content has not appeared; if it ever launched successfully, only `launchCached` is removed from the pipeline. "Successful launch" = RN content-appeared (first native view mounted under the root: ErrorRecovery.swift:306-308, RN RCTRootComponentView.mm:45 / ReactRootView.java:522-526), which in this app is the app/index.tsx boot splash, not "the first screen". UpdatesDatabase.swift:436-440 keeps any update with successful_launch_count > 0 launchable forever even after failures. After content appears, errors within 10 s only run [waitForRemoteUpdate (5 s), crash] (ErrorRecovery.swift:313-322, :205) - no fallback.
Correction: "An update that throws before React Native mounts its first view (the boot splash) on its FIRST launch on a phone is marked failed there and never launched again; the phone relaunches the newest other launchable update or the embedded bundle. An update that has rendered once on a phone is never marked failed there: if it later crashes at startup it crash-loops until a newer update or a rollback directive is downloaded by the ON_LOAD check (the error pipeline waits at most 5 s for that download). Errors more than 10 s after the first view are ignored by expo-updates." Make scenario b assert the failed mark only for a first launch, and add a scenario: U crashes at startup on its second cold start -> phone keeps crashing until halt + rollback-embedded is served.

### F2 (major) Replay of a revoked/halted signed update is accepted; scenario e's pass condition is wrong
Quotes: D12 scenario e "serve an older manifest (replay) ... | all ignored or rejected"; D2 "revoked.txt  update ids that can never be activated again"; D4 "What a stolen leaf allows: someone who also controls the delivery path ..."
Evidence: the client's only freshness rule is launchedUpdate.commitTime < newUpdate.commitTime (PKG/ios/EXUpdates/SelectionPolicy/LoaderSelectionPolicyFilterAware.swift:57). Signature checking has no timestamp, nonce, request binding or revocation: it only checks the chain and each certificate's validity period at verification time (iOS CodeSigning/CertificateChain.swift:76; Android codesigning/CertificateChain.kt:51). revoked.txt exists only on the Pi.
Consequence: anyone who controls Cloudflare, the GCP relay or the Pi - WITHOUT any key - can serve any manifest ever signed by a still-valid leaf (bytes are public: every phone downloads them) to every phone whose running update is older than it, including a revoked bad update. Phones that applied the rollback directive are protected (the directive set their embedded commitTime to bad.createdAt + 1 s). Phones that never received the rollback directive (offline during the incident, new installs of an older binary) accept the replayed bad update for up to the leaf's 400 days. Re-signing with a new leaf does not help: the old leaf still chains to the root until it expires.
Correction: (1) scenario e row: "serve a manifest older than the phone's running update -> ignored; serve a revoked manifest newer than the phone's running update -> ACCEPTED (known limit: the client has no revocation)". (2) D4 add: "Without any key, a party on the delivery path can replay any update signed by a non-expired leaf that is newer than what a phone runs, and can freeze phones with 204." (3) D9 add a step after a bad update: publish a fix (or keep serving the directive) promptly so that every phone's current commitTime passes the bad one, and if the bad update is dangerous, shorten exposure by issuing leaves with a much shorter life (e.g. 90 days) so a revoked update stops verifying sooner.

### F3 (major, only if the section 9 fallback is used) Unsigned manifest filters can downgrade phones if `metadata` is ever non-empty
Quote: section 9 "`Updates.manifest.extra.am` (label, notes, critical) is readable in JS | scenario a; fallback: put them in `metadata` as strings"
Evidence: response headers `expo-manifest-filters` and `expo-server-defined-headers` are NOT signed and are persisted on the phone (iOS Database/UpdatesDatabase.swift:625-644 via RemoteAppLoader.swift:69; Android manifest/ManifestMetadata.kt:80, loader/Loader.kt:131). Filters are matched against manifest `metadata` (SelectionPolicy/SelectionPolicies.swift:8-35); if the running update fails the filters, the client loads a new update "no matter the commitTime" (LoaderSelectionPolicyFilterAware.swift:31-35) and the launcher skips non-matching updates (LauncherSelectionPolicyFilterAware.swift:22-27). With `metadata: {}` filters can never fail (no keys to compare), so the current plan is safe.
Correction: replace the fallback with "fallback: read them from `Updates.manifest.extra.am`; NEVER put fields in `metadata` - it must stay `{}` (non-empty metadata lets an unsigned `expo-manifest-filters` header force a downgrade)". Add to D2: the server never sends `expo-manifest-filters` or `expo-server-defined-headers`; add a drill row: inject `expo-manifest-filters` through the proxy -> no effect.

### F4 (major) A cold start does not APPLY an update or directive that it only downloads; D9 step 4 needs two cold starts
Quotes: D9 step 4 "If the bad update broke `UpdateHost` itself, tell the affected users: iOS, swipe the app away and reopen it; Android, ... Force stop, then reopen. That cold start runs the native check, which needs no JS."; D7 "`ON_LOAD` makes the native code check at every cold start, independent of JS. For a directive, the embedded update's commitTime is bumped in the DB (RemoteAppLoader.swift:245-266) and takes effect at the next launch.
Correction: D9 step 4: "... Force stop, then reopen, wait about 10 seconds with the app open (so the native check can download the fix or directive), then force-stop and reopen it a SECOND time. The first cold start only downloads; the second launches the downloaded code." (Exception: if the bad update crashes before its first view on its first launch, error recovery waits up to 5 s for that download and relaunches in the same session - ErrorRecovery.swift:194-219.) D7: "... the self-repair path: a cold start downloads the fix and the following cold start runs it."

### F5 (minor) `Updates.channel` will always be "production"; telemetry must not use it for beta
Quote: D8 "Events: `ota.boot {updateId, label, runtime, build, isEmbeddedLaunch, isEmergencyLaunch, emergencyLaunchReason, channel}`" and X-AM-Client "`channel=production`".

### F6 (minor) A build-data wipe also deletes the beta opt-in and am_uid
Quote: D5 "The client sends it as `Expo-Extra-Params` on every manifest request and keeps it across launches; changing it deletes nothing."
Evidence: when a later binary changes `updates.url`, `updates.requestHeaders` or `useEmbeddedUpdate`, the wipe also deletes ExtraParams, ServerDefinedHeaders and ManifestFilters (PKG/ios/EXUpdates/Database/UpdatesBuildData.swift:41-44, 95-106; Android db/BuildData.kt:39-53).

### F7 (minor) JS CAN change the baked channel header without disableAntiBrickingMeasures
Quote: D7 "`disableAntiBrickingMeasures: false` means JS can never repoint the update URL."
Evidence: true for the URL (iOS UpdatesConfig.swift:389-398; Android UpdatesConfiguration.kt:194-206), but 57.0.26 exports `Updates.setUpdateRequestHeadersOverride` (PKG/src/Updates.ts:375-379), which is accepted with anti-bricking ON for any header key already in the embedded set, i.e. `expo-channel-name` (iOS EnabledAppController.swift:337-346 + UpdatesConfig.swift:406-441; Android UpdatesConfiguration.kt:212-247). ### F27 [major] The documented backport flow for older runtimes is refused by the publish pipeline's own first step
- Quotes: section 6 "JS fixes for phones still on the older runtime are published from a worktree at the older `native-N` tag with the fix cherry-picked." vs D6 step 1 "Check that the commit is pushed (`git fetch`; it must be contained in `origin/react` or `origin/main`)".
- Problem: a commit made by cherry-picking onto `native-N` is not an ancestor of `origin/react` or `origin/main`, so step 1 refuses it; pushing it to `react`/`main` instead would put old native-era JS on the main line and (with `DEPLOY_ENABLED=true`) deploy the server. Old-runtime phones then cannot get fixes, which is exactly the case section 6 describes.
- Correction: D6 step 1: "it must be contained in `origin/react`, `origin/main`, or `origin/release/native-N` for the runtime being published". Section 6: "Backport: `git switch -c release/native-N native-N`, cherry-pick the fix, push `release/native-N` (deploy.yml does not trigger on it), then `otapublish ota --from release/native-N`." Check that `deploy.yml`'s `on.push.branches` does not include `release/**`.
